# Frontend 开发方案（Campus Fitness Scheduler MVP 重规划）

## 1. 文档目标

本文档用于重新定义 [`frontend/`](frontend/) 前端 MVP 的开发方向，使之严格围绕当前产品目标与现有后端能力展开。

本次重规划后的核心目标不是做一个“大而全”的健康平台，而是做一个**可演示、主链路清晰、能体现 AI 调度价值**的前端 MVP。

当前前端必须围绕以下 5 个能力组织：

- 五步对话式信息收集
- 上传课表入口（第一版先写死/占位）
- 生成训练计划
- 用户不满意时修改训练计划
- 用户询问“现在能不能去训练”时，基于天气/场馆情况回答
- 其他开放问题时，表现为普通 AI 助手式回答

---

## 2. 新的 MVP 产品定义

## 2.1 产品本质

这一版前端不是纯表单，不是纯 Dashboard，也不是纯聊天机器人。

它更接近一个：

- 以对话为入口
- 以结构化计划为结果
- 以修改训练与天气判断为高频交互
- 以普通 AI 问答作为兜底能力

的校园健身助手。

## 2.2 本版 MVP 的演示主线

最重要的演示链路应是：

1. 用户进入页面
2. 与系统完成五步对话
3. 上传课表（第一版前端先假装上传成功，实际提交写死数据或固定 URL）
4. 生成训练计划
5. 用户说“这样不行，我周三不想练/我不想去健身房”
6. 前端调用计划修订接口并刷新计划
7. 用户说“我现在能不能去训练？”
8. 前端调用天气/场馆能力并给出判断
9. 用户问其他问题时，前端进入普通 AI 助手回答模式

这个链路比原来“首页 + 问卷 + 仪表板 + 历史页”更符合你现在要做的产品。

## 3. 当前后端能力与前端映射

## 3.1 已有且可直接使用的能力

### 五步采集
后端已有五步接口：

- `POST /api/v1/chat/step1_profile`
- `POST /api/v1/chat/step2_goal`
- `POST /api/v1/chat/step3_space_time`
- `POST /api/v1/chat/step4_diet`
- `POST /api/v1/chat/step5_habits`

参考实现见 [`backend/app/routers/chat.py`](backend/app/routers/chat.py)。

### 生成训练计划
- `POST /api/v1/plan/generate`

参考实现见 [`generate_plan()`](backend/app/routers/plan_routes.py:47)。

### 修改训练计划
- `POST /api/v1/plan/refine`

参考实现见 [`refine_plan()`](backend/app/routers/plan_routes.py:64)。

### 获取天气/场馆状态
- `GET /api/v1/weather/venue-status`

参考实现见 [`get_venue_weather_status()`](backend/app/routers/weather_routes.py:15)。

## 3.2 目前没有现成接口，但前端要做产品占位的能力

### 上传课表
当前后端在 Step 3 里只有 `schedule_image_url` 字段，没有真正的课表解析闭环。

参考字段见 [`SpaceTimeStepRequest`](backend/app/models/chat.py:82)。

所以第一版前端策略应是：

- UI 上保留“上传课表”按钮
- 实际上传先不做真实文件处理
- 可以直接写死一个图片 URL，或在前端把“已上传课表”作为本地状态
- 最终提交 Step 3 时，把固定的 `schedule_image_url` 传给后端

### 普通 AI 问答
当前后端没有一个明确的“开放聊天回答”路由可直接拿来做普通问答。

因此前端文档上必须区分：

- “计划修改”走 [`/plan/refine`](backend/app/routers/plan_routes.py:64)
- “现在能不能训练”走 [`/weather/venue-status`](backend/app/routers/weather_routes.py:15)
- “其他普通 AI 问题”目前需要新增后端聊天回答接口，或先前端写死 fallback 展示策略

也就是说，**普通 AI 回答这一块，目前是产品目标，尚不是现成后端能力。**

## 4. 新的信息架构

这一版建议不要再以“多页面后台系统”为主，而改成**一个主对话页 + 一个计划展示区**的产品结构。

## 4.1 页面清单

### 1. 首页 / 主入口页
路径建议：`/`

作用：

### 2. 对话式规划页
路径建议：`/planner`

作用：

- 完成五步对话
- 展示课表上传占位

### 3. 训练计划页
路径建议：`/plan`

作用：

- 展示结构化训练计划
- 支持修改计划
- 支持天气训练判断
- 支持回到对话抽屉继续问问题

## 4.2 不纳入本次 MVP 的页面

以下页面从本版开发计划中移除：

- `/history`
- 历史版本详情页
- 复杂 diff 专页

## 5. 核心用户流程

## 5.1 主流程 A：从对话到计划

1. 用户进入 [`/`](frontend/frontend_plan.md)
2. 点击“开始规划”
3. 前端生成或恢复 `session_id`
4. 进入 [`/planner`](frontend/frontend_plan.md)
5. 以对话式卡片完成五步采集
6. 在 Step 3 中展示“上传课表”模块，但第一版实际写死
7. 五步完成后，调用 [`/api/v1/plan/generate`](backend/app/routers/plan_routes.py:47)
8. 跳转 [`/plan`](frontend/frontend_plan.md)
9. 展示结构化训练计划

## 5.2 主流程 B：用户不满意，修改训练

1. 用户在计划页输入：
   - “我不想周三去健身房”
   - “我不喜欢长时间跑步”
   - “帮我把训练挪到周五”
2. 前端调用 [`/api/v1/plan/refine`](backend/app/routers/plan_routes.py:64)
3. 用新返回的 `structured_plan` 覆盖旧计划
4. 展示 `change_summary`
5. 高亮受影响的训练卡片

## 5.3 主流程 C：用户问“现在能不能去训练”

1. 用户在计划页或对话区输入：
   - “我现在能不能去跑步？”
   - “现在适合去篮球场吗？”
   - “下雨了还能不能练？”
2. 前端识别这是天气/场馆判断类问题
3. 调用 [`/api/v1/weather/venue-status`](backend/app/routers/weather_routes.py:15)
4. 根据返回结果生成前端回答
5. 在聊天区显示判断结论，并可同步更新右侧天气卡片

## 5.4 主流程 D：用户问其他普通问题

例如：

- “减脂是不是一定要跑步？”
- “练腿第二天酸怎么办？”
- “蛋白质一天吃多少比较合适？”

这类问题不属于：

- 五步采集
- 计划生成
- 计划修订
- 天气能否训练判断

因此前端需把这类消息归类为“普通 AI 问答”。

但需要明确：

**当前后端未见现成通用聊天接口，所以这一块前端只能先设计交互位与状态机，不应在文档里假设已可直接联调。**

## 6.2 对话式规划页 `/planner`

这是本次 MVP 的核心页面。

### 页面定位

不是传统表单页，而是：

- 左侧/中间展示对话消息流
- 每一步消息下挂可交互卡片
- 用户点击选项或输入内容，驱动五步完成

### 页面结构

```text
+--------------------------------------------------------------------------------+
| Logo                    智能规划对话                               Step 2 / 5   |
|--------------------------------------------------------------------------------|
| 对话消息流                                                                     |
| 助手：先了解一下你的基础信息。                                                 |
| 用户：[已选择 男 / 175cm / 70kg]                                               |
| 助手：你的目标是什么？                                                         |
| [减脂] [增肌] [力量] [爆发力] [耐力]                                           |
|                                                                                |
| （Step 3 时显示）                                                              |
| [上传课表图片]  当前状态：已使用演示课表                                       |
|                                                                                |
|-------------------------------------------------------------- ------------------|
| 输入框：你也可以直接补充说明...                                   [发送]        |
+--------------------------------------------------------------------------------+
```

### 五步设计

#### Step 1：身体基础信息
- 性别
- 身高
- 体重

调用：[`submit_profile_step()`](backend/app/routers/chat.py:60)

#### Step 2：训练目标
- 减脂 / 增肌 / 力量 / 爆发力 / 耐力
- 若选减脂，追问是否接受掉部分肌肉

调用：[`submit_goal_step()`](backend/app/routers/chat.py:81)

#### Step 3：时空约束 + 课表上传占位
- 每周频次
- 单次训练时长
- 上课前 / 下课后 / 无所谓
- 宿舍位置
- 上传课表图片（第一版写死）

调用：[`submit_space_time_step()`](backend/app/routers/chat.py:118)

#### Step 4：饮食预算
- 偏好食堂
- 周预算档位

调用：[`submit_diet_step()`](backend/app/routers/chat.py:142)

#### Step 5：运动习惯
- 喜爱运动
- 是否整合进训练计划

调用：[`submit_habit_step()`](backend/app/routers/chat.py:163)

### 关于“上传课表”的实现策略

第一版建议直接这样实现：

- UI 上允许用户点击上传按钮
- 选中文件后不真正上传
- 前端本地直接标记“课表已上传”
- 提交 Step 3 时传固定值，如：

```json
{
  "schedule_image_url": "https://demo.local/fixed_schedule.png"
}
```

或者直接传一个约定字符串。

这样能保证演示链路完整，但不会引入真实文件上传和视觉模型识别成本。

## 7. 三类用户输入的前端路由策略

本次 MVP 的关键不是单纯做聊天 UI，而是要做**消息分类路由**。

前端收到用户在计划页输入后，需要先判断消息类型。

## 7.1 类型 A：修改训练计划

典型输入：

- “我不想周三训练”
- “不要健身房，换操场”
- “我不喜欢长时间跑步”
- “帮我把训练挪到周五”

处理方式：

1. 调用 [`/api/v1/plan/refine`](backend/app/routers/plan_routes.py:64)
2. 更新计划
3. 展示 `change_summary`
4. 高亮变化项

## 7.2 类型 B：天气 / 场馆判断

典型输入：

- “我现在能不能去训练？”
- “现在适合去跑步吗？”
- “下雨了还能打球吗？”

处理方式：

1. 调用 [`/api/v1/weather/venue-status`](backend/app/routers/weather_routes.py:15)
2. 从 `venue_statuses` 中抽取适合训练的结论
3. 生成前端自然语言答复

### 注意

这里不是 function calling，而是普通天气接口 + 前端规则生成回复。

## 7.3 类型 C：普通 AI 问答

典型输入：

- “练后拉伸多久比较好？”
- “减脂要不要吃夜宵？”
- “为什么我练腿第二天很酸？”

处理方式：

- 第一版先预留统一聊天消息区
- 若后端补出通用问答接口，则接入该接口
- 若暂时没有接口，则前端需展示“普通 AI 问答暂未接通”或使用 mock 回复

### 因此这一块属于

- 产品要设计
- 前端状态机要留口
- 但不能写成“当前可直接联调完成”

## 8. 天气训练判断模块设计

## 8.1 交互定位

“现在能不能去训练”是一个独立高价值动作，应作为计划页显性能力出现。

建议做法：

- 在计划页提供一个快捷按钮
- 在聊天输入框中也支持自然语言触发

## 8.2 前端展示内容

调用 [`/api/v1/weather/venue-status`](backend/app/routers/weather_routes.py:15) 后，前端可展示：

- 当前是否在下雨
- 当前气温
- 适合训练的场馆
- 不适合训练的原因
- 建议改为室内/轻量训练

## 8.3 回答模板建议

前端可按规则拼装回复，例如：

- “现在可以训练，优先推荐街头健身区，地面较干，适合常规力量训练。”
- “现在不建议去天台篮球场，地面过湿，建议改为室内轻量训练。”
- “如果你想跑步，可以优先考虑深圳大学体育场，但请注意弯道防滑。”

这能在没有独立天气 function calling 的情况下，仍然做出可演示的 AI 回答效果。

## 9. 普通 AI 助手区设计

## 9.1 定位

普通 AI 助手不是主流程核心，但它是一个重要兜底。

作用是：

- 让产品显得更自然
- 让用户能问训练常识
- 承接那些不属于“修改计划”也不属于“天气判断”的消息

## 9.2 当前现实约束

由于当前后端未见一个明确的通用聊天接口，所以这一块前端应：

- 先完成 UI 结构和消息分流逻辑
- 暂时使用 mock 数据或占位状态
- 等后端补接口后再接通

## 9.3 文案建议

如果后端未接通，不要报错得太硬，可以提示：

- “普通 AI 问答能力正在接入中，请先尝试训练修改或天气判断。”

## 13. 消息分类器建议

为了实现“同一个输入框，不同问题走不同能力”，前端第一版需要做一个轻量规则分类器。

## 13.1 规则优先级

### 优先级 1：天气/能否训练判断
命中关键词示例：

- “现在能不能”
- “现在适合”
- “能不能去训练”
- “下雨了还能不能”
- “能不能跑步”
- “能不能打球”

=> 路由到天气判断

### 优先级 2：计划修改
命中关键词示例：

- “不想”
- “改”
- “换”
- “挪到”
- “删掉”
- “不要”

=> 路由到计划修订

### 优先级 3：普通 AI 问答
其他情况默认走普通问答

## 13.2 注意事项

这是前端第一版的简单规则，不是最终 NLP 方案。

但对 MVP 非常够用，而且能快速打通演示。

## 15. 开发顺序建议

## Phase F1：基础壳与会话

- 初始化 [`Next.js`](frontend/frontend_plan.md) 项目
- 建立 `session_id` 机制
- 落地首页 `/`

## Phase F2：五步对话式规划页

- 完成 `/planner`
- 接通五步接口
- 加入课表上传占位逻辑

## Phase F3：训练计划页

- 接通 [`/plan/generate`](backend/app/routers/plan_routes.py:47)
- 渲染 `structured_plan`
- 展示 `plan_text`

## Phase F4：计划修改

- 接通 [`/plan/refine`](backend/app/routers/plan_routes.py:64)
- 刷新计划
- 展示 `change_summary`
- 做基础高亮

## Phase F5：天气判断

- 接通 [`/weather/venue-status`](backend/app/routers/weather_routes.py:15)
- 完成“现在能不能训练”回答卡片

## Phase F6：普通 AI 问答占位

- 完成输入分类路由
- 为普通 AI 问答预留 UI 与状态
- 若后端未就绪，则用 mock 占位

## 16. MVP 范围最终定义

## 必做

- 首页
- 五步对话式采集
- 课表上传占位（写死）
- 生成训练计划
- 修改训练计划
- 天气判断“现在能不能训练”
- 普通 AI 问答入口占位

## 可弱化实现

- `plan_text` / `refined_plan_text` 的完整富展示
- 复杂计划 diff
- 多轮历史消息管理

## 不纳入本次 MVP

- 历史计划页
- 真实课表识别上传
- 真正开放式智能体多工具协同
- 完整聊天记忆系统

## 17. 最终建议

这次前端开发应从“页面集合”思路切换到“消息路由 + 计划展示”思路。

最核心的不是堆更多页面，而是把一个输入框背后的三种能力分清楚：

1. 五步规划
2. 修改训练
3. 天气判断
4. 普通 AI 问答兜底

其中，当前可真实联调完成的主干是：

- 五步规划
- 生成计划
- 修改计划
- 天气判断

而“普通 AI 问答”应当在文档和实现上明确标注为：**前端先预留，后端后补。**
